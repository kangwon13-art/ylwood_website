# 프로젝트 컨텍스트 — 영림 재단 최적화 프로그램

> **작업 규칙**: 코딩 작업을 시작하기 전에 이 문서를 먼저 읽고, 여기 적힌 규칙과 맥락 안에서만 작업한다.
> 작업이 끝나면 "진행 상황" 섹션과 관련 항목을 반드시 갱신한다. (사용자 지시, 2026-08-06)

## 1. 프로젝트 개요
- **목적**: 고객이 재단(판재 절단) 리스트를 직접 입력하면 원장(판재) 위에 최적 배치를 자동 계산해 로스율·필요 원장 수·견적가를 즉시 보여주고 주문/견적 요청까지 연결하는 웹 도구.
- **대상 자재**: 합판·MDF 등 판재(2D)만. 몰딩·문틀 같은 선형재(1D)는 범위 밖.
- **핵심 문서**: [`files/재단최적화_기획문서_v1.md`](../files/재단최적화_기획문서_v1.md) — PRD(1부) + 기능정의서(2부) + IA(3부) + 엔진 상세 규칙(4부)로 구성. 새 작업 전 관련 부분을 반드시 확인.
- **엔진 구현체**: [`files/jaedan_engine_v2.js`](../files/jaedan_engine_v2.js) — **v3(2026-08-06 업그레이드)**: 자유직사각형 기반 재귀 길로틴 분할 엔진(스트립 패킹 v2에서 교체). 조각별 독립 회전 결정 + 5개 정렬 × 4개 분할모드(A/B/longAxis/shortAxis) × 2개 회전동점선호 = 총 40개 전략 탐색, 3초 시간제한. 파일 하단에 자체 테스트 스위트 내장(`runEngineTests()`, `window.RUN_ENGINE_TESTS=true`일 때만 자동 실행 — 앱에 로드될 땐 조용히 로드됨), 총 12개 테스트(테스트12는 컷 수 미확정이라 sheets/type만 검증).
  - **컷 수 산정 = 기하학적 최소값**(조각 배치마다 가로/세로 잔여>kerf면 0~2컷) **+ 원장당 전단 1~2컷.** 500×1200×4+400×1200×1(전단O)=8컷, 1220×300×3(전단X)=3컷 두 확정 케이스와 정확히 일치. **단, 현장 실측 컷 수가 이보다 많이 나오는 사례가 최소 1건 있음(§4의 "재단비 현장 실측 불일치" 항목 참고, 미해결).**
- **웹앱(UI)**: [`app/index.html`](../app/index.html) + `app/app.js` + `app/styles.css` — F-01~F-06 3분할 작업화면. 정적 웹앱(백엔드 없음). `../files/jaedan_engine_v2.js`를 그대로 `<script src>`로 로드해 `solve()` 호출.
- **로컬 실행 런처**: [`../재단견적_실행.bat`](../재단견적_실행.bat) 더블클릭 → `app/index.html`을 기본 브라우저로 오픈. 사용법은 [`../사용법.txt`](../사용법.txt) 참고.
- **웹 공유용 단일 파일**: [`webshare/jaedan_app.html`](../webshare/jaedan_app.html) — `app/index.html`+`app/app.js`+`app/styles.css`+`files/jaedan_engine_v2.js`를 전부 하나의 파일로 병합(스크립트 분리 없이 인라인)해 Claude Artifact로 배포한 버전. **로직은 로컬 앱(app/)과 100% 동일해야 한다 — 로컬 쪽을 고치면 이 병합 파일도 반드시 같이 갱신.** 다크/라이트 테마 CSS 변수만 추가됐고 그 외 로직 변경 없음.

## 2. 확정된 핵심 규칙 (기획 문서 기준, 임의 변경 금지)
- **과금**: 재단비만 산출(컷당 과금). 온장 단가는 프로그램에 넣지 않음.
- **재단비 단가표**: 1D/2D × 두께(12mm 기준) 2×2, 코드 고정.
  | 두께 | 1D | 2D |
  |---|---|---|
  | 12mm 이하 | 500원 | 700원 |
  | 12mm 초과 | 700원 | 1,000원 |
- **kerf(톱날 두께)**: 4.5mm. **전단(트리밍)**: 상 14mm(폭 줄임) / 좌 14mm(길이 줄임, 전길이 조각은 생략).
- **결방향**: 사용자가 항목별 체크박스로 직접 선택(엔진이 자동 판단하지 않음).
- **엔진 원칙**: 순수 2D 단일 구조. 별도 1D 로직 없음. 목적함수 우선순위 = 원장 수 최소화 → 로스 최소화 → 컷 수 최소화.
- **미배치 조각은 반드시 사용자에게 명시**(숨기지 않음) — 기획 문서 4.9 및 2.3.
- **관리자 페이지 없음** — 단가·kerf·전단 값은 전부 코드에 고정.

## 3. 실행/테스트 환경 메모
- 이 환경에는 **Node.js가 설치되어 있지 않음**. `jaedan_engine_v2.js`를 실행/검증할 때는 Claude Browser로 HTML에 인라인 스크립트로 감싸서 브라우저에서 실행하고 `get_page_text`로 console.log 출력을 확인하는 방식을 사용한다.
  - `file://` 경로가 "프로젝트 폴더 밖"이면 정적 스냅샷으로만 렌더링되고 JS가 실행되지 않을 수 있으니, 테스트용 HTML은 반드시 `files/` 폴더 안에 임시로 만들고 확인 후 삭제한다.

- **사용자가 실제 재단기 출력 사진을 제공**: 400×1200×1 + 600×1500×1 + 600×1000×2 케이스(4x8/18T/전단O)를 실제 재단기 소프트웨어가 계산한 화면 캡처. 표 구조를 분석한 결과, 이 배치는 정확히 **9컷**으로 확인됨 — 웹앱이 방금 재확인한 값(9컷·9,000원, 원래 스크린샷과 동일)과 **정확히 일치**. "8컷"이라던 이전 답변은 캐싱 버그로 인한 오답이었고 지금은 정정됨.
  - 재단기 출력 해석: 재단치수/수량/잔여치수 테이블에서 **잔여치수가 음수(거의 0)로 나오는 행은 남은 자재를 그대로 다 써서 별도 컷이 필요 없다**는 뜻 — 이게 정확히 우리 엔진의 "잔여가 kerf 이하/음수면 컷 안 셈" 규칙(`MIN_CUT`)과 일치함. 이 규칙 적용해서 9컷으로 수동 검산 → 엔진 값과 일치.

- **결론**: 이 특정 배치 유형(길이축 분할 → 폭축 분할 → 길이축 분할, 3단 재귀)은 **엔진이 정확함이 실측으로 검증됨**. 이전 §4의 "재단비 현장 실측 불일치"(400×1200×2+1500×600×1+800×600×2 → 14컷 vs 엔진 10컷)는 **다른 케이스**이며 여전히 미해결 — 그 케이스는 #1·#2가 동일 규격(400×1200)으로 나란히 이어지는 구조가 섞여 있어서 다름. 두 케이스를 혼동하지 말 것.
